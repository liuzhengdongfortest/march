# 决策记录

日期：2026-05-10

## 决策 1：竞品参照体系

**决定**：以 Claude Code、OpenCode、Codex 为 March 的三大参照竞品，持续跟踪。

**原因**：
- Claude Code：市场领导者（$1B 收入），产品体验和生态最成熟
- OpenCode：开源标杆（95K Stars），多提供商支持和 TUI 设计最值得学习
- Codex：Rust 实现的沙箱安全性是差异化，/goal 自主循环是独特能力

## 决策 2：差距优先级

**决定**：分四个 Tier 推进差距补齐。Tier 0（桌面级缺失）最优先，Tier 2（体验打磨）与 Tier 0 并行——UI 不能等。

**Tier 0**：MCP 支持、Web 搜索/抓取、权限分级、多提供商
**Tier 1**：Plan 模式、子 Agent、撤销/重做、IDE 集成、图片/PDF
**Tier 2**：TUI 视觉重设计、安装体验、配置系统、自动模型切换
**Tier 3**：自主循环、Hooks、沙箱安全、CI/CD、Agent SDK

待老板确认是否创建对应 Roadmap。

## 决策 3：Prompt 双轨优化策略

**决定**：Prompt 优化分两条轨道同时推进。

**轨道一：竞品 Prompt 萃取。** 从 Claude Code、OpenCode、Codex 的源码中提取系统提示词，对比 March 当前 prompt，学习竞品在工具调用精确度、错误恢复引导、安全边界措辞、上下文利用策略上的写法。

**轨道二：元调试（Meta-Debugging）。** 让 March 自己给自己看病——在 March 里以 "你现在在一个名为 March 的 Agent 容器里" 的角色提示，让 DeepSeek 试功能、找不顺手的地方。AI 从内部感受到的问题（prompt 矛盾、工具返回格式难解析、上下文切换不自然）是开发者视角的盲区。

**原因**：
- 竞品 prompt 是经过大量迭代打磨的结果，直接参考比从零优化高效
- 元调试利用了 AI 的元认知——它既是使用者又是被调试对象，能发现人类不会注意到的问题
- 两条轨道互补：竞品 prompt 提供"别人怎么做的"，元调试提供"March 自己觉得哪不对"

**元调试覆盖清单**：每个工具的使用体验、每种交互模式的流畅度、边界情况（空状态、错误态、长输出截断、并发场景）、prompt 指令的清晰度和一致性。

## 决策 4：元调试必须结合源码审查

**决定**：元调试不止让 AI 体验功能接口，必须同时阅读对应的源码实现，从代码层面发现设计问题。

**原因**：
- 容器暴露的接口掩盖了实现细节：状态机缺陷、竞态条件、缓冲区边界、错误传播断裂这些问题从接口行为很难暴露
- AI 同时扮演"使用者"和"代码审查者"两个角色，能交叉验证——接口行为异常时追溯源码根因，源码设计可疑时验证接口表现
- March 理论上能自举（自己改自己），但当前还不够成熟，由 AI 助手扶着：助手设计元调试提示词、执行 March 自诊断、根据诊断结果修改代码

**元调试三层深度**：
1. 表层——用工具，感受 prompt 清晰度、返回格式、交互节奏
2. 源码层——读对应实现，找状态管理、并发、边界处理问题
3. 交叉层——接口异常追溯到代码根因，代码可疑验证接口表现
